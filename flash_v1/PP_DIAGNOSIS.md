# 8卡 PP 误定位诊断（2026-10-22）

本文件保留初始诊断。用户后续已授权优化；最新修正及rank7独立实测见[PP定位修正与验证](PP_OPTIMIZATION.md)。下文“未改/未跑”指初始诊断阶段。

结论：现有结果不能直接归为“论文方法的适用边界”。已经确认消息尺寸分组与计分耦合的适配问题，以及原生PP bucket布局不对称造成的跨stage可比性缺口；PP等待传播是有结构依据、尚未由时间线证实的解释。没有证据把问题归为训练梯度错误，也没有证据证明修正重复计分即可定位rank7。当前仍处复现阶段，PP问题解决前不扩卡、不增加并行配置。

## 1. 论文实际要求与覆盖

页码为印刷页 / PDF页（1-based），来源为根目录《中文论文.pdf》及《greyhound.pdf》。

- 中文论文34 / 50页明确允许单clique跳过组间筛选进入rank分析；这一规则本身不是实现bug。但该候选不具有跨clique筛选证据，不能把本轮dense_DP描述为成功完成了跨stage筛组。
- 31 / 47页说明多标签一致可提高置信度；45 / 61页定义累积得分为参与并行组得分之和。没有依据将同一个并行组的多个消息尺寸视为新增独立并行组。41–42 / 57–58页分别给出组得分、rank得分；不应擅自把二者相加来修复本例，实验措辞仍存在歧义。
- 44–45 / 60–61页含16GPU混合配置EP4/TP1/PP2及EP4/TP2/PP2、单GPU锁600MHz的得分实验；因此不能说论文没有PP实验。该实验不等于验证任意8GPU PP配置的准确率，原文也承认PP时延分离较弱。
- 46–47 / 62–63页承认不同消息规模、不同算子阶段的绝对时延比较会误定位，并把流水线气泡建模列为未来工作。Greyhound印刷737 / PDF8页要求可比集有相同数据传输量；均分层数不自动保证本适配的梯度buffer体量及通信时序相同。

## 2. 从原始数据确定的错误选择链

输入为 `results/stage3_pp_sustained/profile_1.json` 的7,144条记录。离线重放与原 `events.jsonl` 一致（浮点容差1e-12）；真值rank7，最终rank3。

1. 原始Megatron `distributed_data_parallel.py:60–68` 对非首PP stage禁用bucketing。本例前stage为19个dense / 31个expert bucket，后stage为1 / 1；不是本轮私改DDP造成的。
2. `topology.py:80`为避免跨消息尺寸混比，将语义标签拼成 `label:count:dtype`。该比较隔离有必要；但前后stage没有共同的dense count，所以每个dense子标签只剩一个clique，按论文允许的单clique规则直接进入rank分析。**没有“先确认哪个stage异常”的有效dense组间筛选。**
3. `analysis.py:145–150`又将这些尺寸子标签当作累加单位。同一前stage dense clique获得两份有效分数，同一expert clique也获得两份；后stage只获得一份dense分数。消息尺寸分组被当成参与并行组，导致权重依赖bucket布局，属于适配层的问题。

| 真正通信组 / 消息count | 候选rank | rank得分 |
|---|---:|---:|
| 前stage Expert_DP [1,3] / 2,179,072 | 3 | 0.416530 |
| 前stage Expert_DP [1,3] / 688,128 | 3 | 0.258854 |
| 前stage dense_DP [0,1,2,3] / 2,552,960 | 3 | 0.718894 |
| 前stage dense_DP [0,1,2,3] / 2,898,560 | 3 | 0.698938 |
| 后stage dense_DP [4,5,6,7] / 194,298,880 | 7 | 0.524415 |

由此rank3=2.093216，rank7=0.524415。后stage Expert_DP同尺寸两组CV=0.02279，按0.1阈值跳过，并未提供rank7的第二标签。

**重复计分不是唯一原因。** 离线按每个语义家族取max，rank3仍1.135425；取mean仍1.046608，均超过rank7的0.524415。每rank用中位数替换平均数，仍是rank3。前stage的rank3短通信信号确实存在，不能解释成单个离群样本或只靠去重便能消除。两种家族聚合仅用于敏感性分析，不是已选定的论文修复。

反向对照：直接删count、混合所有消息尺寸会得到rank7，但这是破坏可比性的错误修法，**不能算定位成功**。

## 3. 尚不能由已有数据确定的因果

- 真值rank7与rank3属于PP链[3,7]。rank7反向迟到可经P2P使rank3迟到，rank3在自己的DP/Expert_DP里于是也可能最短；因此两个标签同指rank3不自动证明rank3是故障源。现有证据支持这一机制的可能性，不能证明它解释了全部时延差异。
- 原生1F1B只在最后微批开放梯度同步，前一微批的迟到可能已被PP/EP传播。适配继承 `batch_p2p_sync=True` 的P2P后设备同步，未额外发明此同步；它会影响等待出现的位置，不能仅凭静态源码量化影响。
- `native/probe.cpp:55–64,91`在PROFILE同步end event，会改变异步DDP重叠。这与论文的同步计时设计一致，不能直接当实现bug；但它是需要测量的干扰项。本例每个(rank,group_id)仅一条记录，没有“多操作共享一次group时长”导致误判的证据。
- 已存profile经 `control.py:37–43` 丢弃调用时间戳及buffer地址，没有step/microbatch/bucket身份；健康对照处于MONITOR，没有对应CUDA时长基线。无法区分rank3原有调度偏差、PP传播和PROFILE同步扰动的贡献。
- 延迟只注入rank7的本stage backward，注入迭代与报警吻合；125ms单段校准有效，但每步250ms是按2微批配置推算，尚未记录实际hook调用数与累计执行延迟。不能把训练步净增量不足250ms视为注入失败。
- 实际成员映射正确，PP/embedding组已排除；8GPU FP32梯度及更新验证支持训练适配正确，但不证明通信定位假设成立，也不覆盖已保留的BF16逐元素失败。

## 4. 修改与重测的决定

**需要先做有限适配修正与可观测性补齐，再决定方法层面是否需要变化；8卡短对照有必要，大规模重测没有必要。** 本轮只完成诊断、离线重放及文档纠偏，未改检测/定位/训练算法，未运行GPU。

下一阶段限定为：

1. 分离“真实并行组/语义标签”和“count/dtype比较子集”，消除bucket尺寸改变参与组计分权重的隐式行为；明确单clique、跨stage不可比和冲突证据。具体族内归并规则须说明论文未给出的部分，不能因哪条规则能选rank7就采用它。
2. 保存原始时间戳、buffer/bucket对应关系及step/微批/就绪时刻；最少记录PP收发等待、实际注入hook次数和probe同步开销。优先使用已有身份与时间点，避免增加训练同步。
3. 固定本次8卡PP2/EP2/ExpertDP2、阈值、注入rank/位置/强度，先做短健康PROFILE与同配置持续慢PROFILE对照；核对真实通信时序及可比性。不要强改原生bucketing、删除count混比、搜索注入点或调阈值来制造正确输出。
4. 若修正适配后、在可比通信证据中仍观察到rank7→rank3传播且原论文规则不能区分源rank，才把该部分确认为方法在此配置的限制；任何新增因果定位规则需另列为方法扩展，不能冒充复现。

验收重点是能解释错误来源并如实呈现证据；最终选对rank7仍需独立运行验证。原误定位记录永久保留，不能被离线反事实覆盖。
